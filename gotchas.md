# Gotchas

- **The lunaroute/GLM gateway is lenient about the tool-call protocol.** During the
  jam, a variant pushed assistant messages *without* their `tool_calls` field and
  three live runs still passed — a strict OpenAI endpoint would 400. Green e2e runs
  against this gateway do NOT prove protocol correctness; check the message shapes.
- **`.env` at repo root holds a live lunaroute API key.** Gitignored from commit
  zero. Never commit it, never echo it. Bun auto-loads it from CWD, so run
  `bun test` and the agent from the repo root.
- **Transcripts anchor to the source dir, not `--cwd`.** `.transcripts/` lives next
  to the code (via `import.meta.dir`), so runs never litter the target repo. A jam
  variant got this wrong and wrote ghost files into its own source tree — that's
  why the anchoring happens *before* `process.chdir`.
- **stdout purity is a contract.** One-shot mode: stdout carries only the model's
  final prose (pipe-safe); progress lines and the stats line go to stderr. Don't
  add `console.log` calls.
- **Tail-truncation is deliberate.** The 8000-char tool-output cap keeps the LAST
  8000 chars because test failures live at the end of output. This applies on the
  bash-timeout path too (partial output is capped — regression test exists).
- **YOLO is a feature.** No permission prompts anywhere, by explicit decision.
  Don't "helpfully" add confirmation gates.
- **SIGHUP handler registered at module load, not in main().** The signal handler calls `doReload` with whatever `_sighupSystemPath` is set to (defaults to `system.txt`). main() updates `_sighupSystemPath` if `--system` was passed. Tests that import index.ts without calling main() will still see the SIGHUP handler registered.
- **`doReload` uses cache-busted dynamic import.** `import(path + '?v=' + Date.now())` — verified working in Bun 1.3.14. If you pass the same path twice, the query-string suffix forces a fresh module load. Without it, Bun returns the cached module.
- **`spawn_agent` depth guard uses env var, not argument.** `BREAK_AWAY_DEPTH` is inherited by child processes and incremented on each spawn. Never pass it explicitly to the child; let env inheritance handle it. `BREAK_AWAY_MAX_DEPTH` defaults to 3.
- **Compiled binary (`bun run build`) has embedded FS.** `import.meta.dir` = `/$bunfs/root` in the binary — paths anchored there are read-only and break at runtime. Fixes: text import bundles system.txt; transcripts redirect to `~/.break-away/transcripts`; spawn_agent uses `process.execPath` for children. `bun test` runs from source — these paths are never hit during tests, which is by design.
- **SIGHUP / `/reload` in binary warns, doesn't reload.** The binary is a frozen snapshot. Rebuild (`bun run build`) to pick up source changes.
- **Pid-reuse in agent state derivation.** State is derived via `process.kill(pid, 0)`: running if alive, died if not, done if an `agent_done` record exists. If the OS recycles a dead child's pid and hands it to an unrelated process, that child will report as `running` instead of `died`. Accepted for this playground; note it if debugging unexpected state.
- **`diffAgentStates` returns `AgentTransition[]`, not strings.** Changed in the lifecycle-color pass. Use `formatTransition(t, renderCfg)` from `render.ts` to format for display. Don't grep for the old string-format assertions.
- **`verifySpawn` adds ~700ms to every spawn.** This is intentional — nohup returns a pid even for corpses, so we wait 700ms then check. Spawns are rare. E2e tests with tight timeouts may need bumping if total time creeps up.
- **`/restart` and `SIGUSR2` now write `agent_done` before exiting.** The record is written synchronously (appendFileSync inside async wrapper) so calling without await just before `process.exit` is safe. This prevents the old pid from reading as "died" after a clean restart.
- **Bun timer `unref()` works as expected.** Verified in Bun 1.3.14: `setInterval` returns an object with an `unref()` method; calling it prevents the timer from keeping the process alive after the main work finishes. The poller uses this — a one-shot run exits promptly without needing `clearInterval` on every path (though `stopPoller()` is also called for cleanliness).
- **Models misread combined commands that partially time out.** Observed live (2026-08-30): a parent agent ran `cat file; ls; find / -maxdepth 6` as ONE bash call — the cat succeeded but the find hit the 30s timeout, and the `[timed out]` marker made the model treat the whole result as failure and loop retrying. The model sees one result string per call; a timeout marker poisons everything bundled with it. If an agent loops on "failing" commands that should work, look for this.
- **Tool output is redacted before the model or transcript ever sees it.** `redactSecrets` (src/redact.ts) runs at a single chokepoint in `executeToolCall` (agent.ts), so every tool result — success, error, and retry — is scrubbed of PEM private keys, provider keys (`lr_`, `sk-`/`rk-`/`pk-`), bearer tokens, AWS `AKIA…` ids, and sensitive `KEY=VALUE` env assignments before it reaches messages OR the JSONL transcript. If a real value shows up as `[REDACTED]` while debugging, that's why — the raw value is intact on disk, only the agent-visible copy is scrubbed. The env-assignment rule is deliberately aggressive (any key name containing KEY/SECRET/TOKEN/PASSWORD/PRIVATE/CREDENTIAL/AUTH), so it can over-redact code like `API_KEY = process.env.X`; that's the safe direction.
- **No turn limit by default; `--max-turns N` is an explicit safety/debug cap.** `defaultPolicy.maxTurns` and `seriousPolicy.maxTurns` are both `Infinity` — a run ends when the model finishes (or errors/aborts), not at an arbitrary count. Deliberate (Doc Bizmarkie's "don't die at 30 turns"): the container/VM is the real boundary, not a turn counter. Two consequences. (1) A model stuck tool-calling forever will loop forever — `--max-turns N` is the valve, and hitting it returns `stopReason: 'maxTurns'` (incomplete) and makes the one-shot process exit NONZERO. That mapping is `exitCodeForStopReason` (index.ts): only `done` → 0, every other terminal state (`maxTurns`/`error`/`aborted`) → 1, applied via `process.exitCode` (not `process.exit`) so stdout and the transcript still flush first. (2) There is NO forced tool-less final turn — the old "reserve the last turn for prose synthesis" behavior is gone. Every turn, including the one that hits an explicit cap, is called WITH the full tool set, so a capped run can end mid-work on a tool call; that partial transcript is preserved rather than replaced by a synthesized answer.
- **The bash tool kills the whole process GROUP on timeout, not just bash.** The handler spawns with `detached: true` (child leads its own process group) and, on timeout, runs `process.kill(-proc.pid, 'SIGKILL')`. Why it matters beyond an orphan leak: a backgrounded child (`nmap … &`, `sleep 30 &`) inherits bash's stdout pipe, so killing only bash leaves the pipe open and `new Response(proc.stdout).text()` never resolves until the child dies on its own — the handler HANGS for the child's full lifetime. The group kill reaps the child, closes the pipe, and the read returns promptly with partial output. The timeout message now reads `process group killed`. The negative-pid kill is safe precisely because `detached` puts the child in its own group — it can't hit our own process group.
- **Tool handlers validate required string args before executing.** Each handler (`read_file` path, `write_file` path/content, `bash` cmd, `spawn_agent` task) checks `typeof x === 'string'` (and non-empty, except `write_file` content where an empty file is valid) and returns `error: missing required field: <field>` before touching the shell or file API. Root cause it fixes: a model sent `{"command": …}` instead of `{"cmd": …}`, so `undefined` reached `bash -c` / `Bun.write` / the spawn arg-escaper (which crashed on `undefined.replace`). Validation runs INSIDE the handler, so it protects every call path, and the redaction chokepoint still scrubs the error string like any other tool output.
- **`edit_file` is exact-match-or-refuse, and replaces by index (not `String.replace`).** It counts non-overlapping occurrences of `old_text` via `content.split(old_text).length - 1`; zero matches → actionable error telling the model to re-read, more than one → ambiguity error with the count — both leave the file byte-for-byte unchanged. No fuzzy matching by design; exact failure is the useful feedback. The single-match replace is done with `slice(0, idx) + new_text + slice(idx + old_text.length)`, NOT `String.prototype.replace`, so `$&`/`$1`/`$<name>` in `new_text` are written literally instead of being interpreted as replacement patterns (a real corruption trap). `new_text` may be empty — deleting `old_text` is a valid edit — so only `path` and `old_text` must be non-empty. The write is atomic: stage to `.<name>.edit-<pid>.tmp` in the SAME directory, then `rename` over the target, so a crash mid-write can't leave a partially written file (cross-dir rename would break atomicity, hence same-dir). Success reports the affected 1-based line range and resulting char count.
- **`--serious` is a profile bundle, not a turn number.** `seriousPolicy` (policy.ts) is `{ ...defaultPolicy, apiMaxAttempts: 5, completionAudit: true }` — more blip-survival and a completion audit, sharing the default's unbounded horizon (both inherit `maxTurns: Infinity`). `selectPolicy({ serious, maxTurns })` is the single seam that turns CLI intent into a Policy: no flags → `defaultPolicy` by reference; `--serious` → `seriousPolicy` by reference; an explicit `--max-turns` then imposes a turn cap on top, so `--serious --max-turns 120` keeps `apiMaxAttempts: 5` but stops at 120 (and exits nonzero if it gets there). Precedence is explicit-flag > profile > default. Caveat: `doReload` (SIGHUP / `/reload`) re-imports `defaultPolicy` from policy.ts, so a hot-reload mid-run discards the `--serious`/`--max-turns` launch choice and reverts to the default policy — already true for `--max-turns`, now also for `--serious`.
- **The completion audit gives the model exactly one enforced re-check before a no-tool finish counts as done.** With `policy.completionAudit` on (off in `defaultPolicy`, ON in `seriousPolicy`), the FIRST time the model tries to finish (no tool calls and `shouldContinue` false) the loop does not return `done` — it sets a per-run `completionAuditTriggered` flag, emits a `completion_audit` event, appends a user message (`COMPLETION_AUDIT_PROMPT`: "Before finalizing, audit the task against the requested observable outcome…"), and `continue`s so the model is called AGAIN with tools enabled. The model can then verify/fix; its next no-tool finish returns `done` normally (the flag blocks a second audit — no loop). Two design bolts: (1) the audit is a `continue`, never a manual `chat()` call, so the loop's own `turns < maxTurns` guard makes an over-budget call structurally impossible; (2) it fires ONLY when `turns < maxTurns - 1`, so with an explicit cap the injected audit turn always has budget to actually run — at the ceiling the guard returns `done` instead of appending a prompt no turn would answer. With no turn limit (the default) `maxTurns` is `Infinity`, so the audit always fires exactly once. Consequence for tiny explicit budgets: `--max-turns 2` with a premature finish on turn index 1 never audits (1 is not `< 1`); a genuinely-no-tools task in serious mode still finishes, just one audit turn later. The audit turn counts against the turn budget like any other.
- **`read_file` pages by line window, and windows reconstruct the file exactly.** The tool takes optional `start_line` (1-based, default 1) and `max_lines` (default 400). The line model is `text.split('\n')` — a perfect inverse of `join('\n')` — so paging a file with `max_lines` and concatenating the bodies with `\n` reproduces the original byte-for-byte, including a final line with no trailing newline and the empty file (`['']`). Backward-compat path: a call with NO range args and a file that fits under both the line default and the 8000-char `OUTPUT_CAP` returns the raw text with no metadata line, exactly like the old tool — existing callers and tests don't see a behavior change. The moment a range is requested OR the file is too big, the result is prefixed with one metadata line: `[lines 401-650 of 2137; next_start_line=651]` while more remains, or `[lines 2100-2137 of 2137; end of file]` on the final window (no `next_start_line`, so the model has a definite stop signal). The cap is enforced by dropping WHOLE lines off the end and reporting the range actually returned — the metadata never lies about what you got — except a single requested line longer than 8000 chars, which is head-truncated with `[line truncated]` (head, not tail, because when you asked for one specific line you want its start; this is the opposite of the bash/tool-output cap, which keeps the tail where failures live). `start_line` past EOF is an actionable error (`start_line 500 is past end of file (120 lines)`), and non-integer or `< 1` `start_line`/`max_lines` are rejected before the file is opened. Note the default window is 400 lines but the old whole-file cap was purely 8000 chars: a file of 300 lines that's over 8000 chars now returns a windowed+metadata result where before it returned tail-truncated text.
- **Transient API errors are retried in-loop, and a retry does NOT cost a turn.** `callChatWithRetry` (agent.ts) wraps every `chat()` call BELOW the turn counter, so a gateway blip mid-run costs backoff time, not a turn — the whole point is that a 25-turn investigation survives one bad response instead of dying with `stopReason: 'error'`. Default `apiMaxAttempts: 3` lives in `defaultPolicy`, so the DEFAULT agent is resilient, not just a special profile. Classification mirrors the OpenAI SDK's own `shouldRetry`: connection errors (no numeric `status`) plus 408/409/429 and any 5xx are transient; every other 4xx (401, 400, 404) is permanent and rethrows on the first try. Backoff is exponential with 0.5×–1.5× jitter off `apiRetryBaseMs` (750ms). **This layers on TOP of the SDK's own retries** (maxRetries defaults to 2 in client.ts), so a single model call can make up to `apiMaxAttempts × 3` HTTP attempts before the run finally dies — by design, more survival headroom. The `api_retry` event carries the status only (`HTTP 503`), never the error body, so provider payloads and any embedded key material never reach the transcript. Deferred for v1: honoring the server's `Retry-After` header (the SDK layer underneath still honors it).
